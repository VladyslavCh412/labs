# FleetFlow: архітектурна документація ЛР8

Варіант 12. Стан реалізації та локальні вимірювання: 03.11.2026.
Цей пакет описує кінцевий код `lab8final/` та включені підтвердження попередніх етапів.
Він замінює посилання на відсутні у репозиторії попередні PDF/PPTX.

## 1. Огляд системи та межі

FleetFlow обліковує автомобілі, водіїв, маршрути й рейси. Диспетчер створює
рейс, починає перевезення і завершує його із зазначенням пробігу. Керівник
керує автопарком. Спостерігач читає дані. Фактичні зовнішні актори — ці три
ролі та браузер користувача. Картографія, GPS/телематика й зовнішні SMS/e-mail
є частиною початкового задуму, але не підключені до цього прототипу.

| Зацікавлена сторона | Інтерес | Пріоритет |
|---|---|---|
| Диспетчер | Призначення та контроль рейсів | Швидкодія, актуальність |
| Водій | Коректне призначення та допуск | Цілісність, доступність |
| Керівник автопарку | Стан ТЗ і пробіг | Точність, безпека |
| Механік | Своєчасне ТО | Цілісність стану ТЗ |
| Адміністратор | Доступ, резервування, запуск | Безпека, відновлення |
| Бухгалтер | Облік використання транспорту | Точність пробігу |
| Замовник перевезень | Прозорий стан виконання | Надійність |
| Розробник | Передбачувані зміни | Підтримуваність |

## 3. C4: контекст, контейнери, компоненти

Джерела діаграм: `diagrams/context.mmd`, `containers.mmd`, `components.mmd`;
поряд збережені SVG. На L1 FleetFlow показано одним елементом.
Суцільні зв'язки означають реалізовані HTTP/SQL-виклики; пунктирні —
асинхронну доставку. Світлі елементи на L1 — зовнішні системи з плану.

Strategy викликається робочим Dashboard/Gateway через resolve_target; запит до неправильного власника ресурсу відхиляється.

L2: браузер звертається лише до Dashboard/Gateway (FastAPI, :8000). Fleet
(:8101) володіє fleet.sqlite, Trips (:8102) — trips.sqlite. Event Bridge
отримує outbox Fleet через HTTP, надсилає події Trips і підтверджує доставку
лише після успіху. Trips Worker належить контексту Trips і читає тільки його
outbox. Сервіси не читають чужі БД.

L3 деталізує тільки Trips: HTTP-контролери й JWT guard; TripUseCases;
домени та порти TripStore/FleetGateway; SQLite repository; HTTP adapter;
кеш сторінок; Observer-підписники. Factory збирає конкретні залежності.
`application.py` імпортує тільки домен, що контролюється fitness-функцією.

Фронтенд реалізовано на TypeScript 7.0.2 у `frontend/src/app.ts`: strict і noEmitOnError, типізовані DTO та API-клієнт. `npm run build` створює runtime JS; FastAPI роздає тільки `frontend/build`. Node.js 24 використовується для збірки. Бекенд — FastAPI + SQLite. Джерело рішення — ADR-013.

## 4. Архітектурні рішення та еволюція

Початкове рішення — модульний моноліт (ADR-001); після ЛР3 deployment
замінено Fleet + Trips (ADR-003). Технологічний стек FastAPI/SQLite збережено
(ADR-002). Python у перевіреному середовищі — 3.13.14. SQLite обрано для
простого локального стенду; незалежні процеси додають мережеві відмови.

| Критерій | Модульний моноліт | Моноліт + worker | Fleet + Trips |
|---|---|---|---|
| Простота розробки/експлуатації | Найкраща: один deployment | Потрібен фоновий процес | Більше процесів і конфігурації |
| Ізоляція відмов | Спільний процес | Worker ізольований | Fleet/Trips мають незалежні збої |
| Цілісність | Одна локальна транзакція | Локальні транзакції та outbox | Лише локальний ACID, повтори й проєкції |
| Перевірюваність меж | Дисципліна імпортів | Додаткові тести worker | Контракти, тайм-аути, власник даних |

Журнал з 14 рішень — `docs/adr/INDEX.md`. Оригінальні ADR-001–003 залишено
незмінними. Індекс явно вказує заміну ADR-001 на ADR-003. Нові ADR-011/012/013
датовані 03.11.2026, не заднім числом.

## 5. Чотири шари та бізнес-правила

Поточний продукт містить усі чотири шари: presentation — trips_service/app.py; application — trips_service/application.py; domain — trips_service/domain.py (сутності та Protocol-порти); infrastructure — repository.py і fleet_client.py. Складання залежностей — factory.py та create_app. Сценарії create/start/complete звертаються до портів, а не конкретного SQLite. Vehicle і Driver належать домену Fleet, Trip і Route — домену Trips. HTTP DTO не проходять у SQLite напряму.

Правила: ідентифікатори рейсу обов'язкові; маршрут містить >=2 непорожні
точки; пробіг не від'ємний; початок можливий лише для planned, доступного
ТЗ і допущеного водія; ТО заборонено під час активного рейсу; завершення
можливе лише для active. Завершення повертає ТЗ у available і додає пробіг.

Початок двох різних рейсів на одному ТЗ серіалізується `BEGIN IMMEDIATE`
у Fleet. Квитанція `{trip_id}:{operation}` і зміна ТЗ комітяться разом.
Повтор з іншим пробігом відхиляється 409. Trips записує власний перехід
після успішної команди Fleet. При втраті відповіді або локальному збої
той самий повтор безпечно завершує операцію. Автоматичний recovery worker
для цих команд поки не реалізовано: це явний технічний борг.

## 7. Архітектура даних

| Сутність/таблиця | Власник | Споживач і спосіб доступу |
|---|---|---|
| Vehicle, Driver, vehicle_usage | Fleet | Trips: HTTP GET і внутрішня команда |
| command_receipts, vehicle_outbox | Fleet | Bridge: лише HTTP outbox/ack |
| Route, Trip, trip_operations | Trips | Dashboard: API Trips |
| vehicle_snapshot | Trips, похідна проєкція | Оновлюється лише подіями Fleet |
| notification_inbox, outbox | Trips | Окремий worker контексту Trips |
| Хеші облікових записів | Auth/bootstrap | Сервіси отримують claims JWT, не пароль |

Локальна копія містить лише id, plate, status, version, updated_at.
Вона потрібна для відображення останнього відомого стану; рішення про
відправлення рейсу перевіряються у власника Fleet. Дані посвідчення водія
та пробіг не копіюються. Міжсервісні посилання — id, без cross-DB FK.

Міграція ЛР5: 001_expand додає registration_number; 002_dual_write
підтримує паралельний запис; 003_switch_reads переводить читання;
004_contract вилучає plate тільки після переходу споживачів. Тест перевіряє
кожен етап, доступ старого споживача до contract та повторний запуск.
Адитивна feature-міграція `fleet_service/lifecycle/001_usage.sql` додає
стан використання і квитанції, не змінюючи чотири історичні етапи.

| Кеш | Ключ | TTL/місткість | Інвалідація |
|---|---|---|---|
| VehicleReadCache | vehicle_id | 30 с | Зміна status, registration та lifecycle |
| TripPageCache | limit, offset, active | 1 с, 128 ключів | Create, start, complete рейсу |

Промах звертається до власного repository. Кеш сторінок має single-flight:
конкурентні однакові запити не запускають кілька loader. Кеш локальний
для процесу, тому інший процес бачить зовнішню зміну протягом TTL.

Fleet у тій самій транзакції з мутацією пише VehicleStatusChanged.
Bridge повторює доставку при відмові й ack-ає тільки підтверджену подію.
Trips у транзакції записує inbox event_id та оновлює snapshot тільки за
більшої version. Дубль не змінює стан; старі події не відкочують нові.
Номер автомобіля також породжує подію. Звичайний інтервал polling — 0,5 с;
за outage верхньої межі відставання немає, що прийнятно для read-only
проєкції, але не для рішення про відправлення ТЗ.

## 8. Безпека та модель загроз

Межі довіри: браузер → Gateway (пароль/JWT, DTO); Gateway → власник
ресурсу (JWT, DTO); Trips → Fleet (service JWT, команда); Bridge → API
обох сервісів (service JWT, подія); процес → власний SQLite/локальні файли.
Усі сервери слухають лише loopback. Shared HS256 означає взаємну довіру
локальних процесів; для незалежних зон довіри потрібні асиметричні ключі.

| STRIDE-загроза | Вплив / імовірність | Захист і залишковий ризик |
|---|---|---|
| Підроблений/прострочений JWT | Високий / середня | HS256 allowlist, exp/iss/aud/iat/jti; 401 |
| Прямий обхід gateway | Високий / висока | RBAC у Fleet і Trips; 403 у прямих запитах |
| Викрадення пароля/підбір | Високий / середня | Argon2id, випадкові паролі, 10 спроб/хв на адресу |
| Підміна внутрішньої команди | Високий / середня | Лише роль trips-service; людські ролі відхиляються |
| Повтор/перестановка подій | Середній / висока | inbox event_id + monotonic version |
| SQL injection / невалідний DTO | Високий / середня | Параметризований SQL, Pydantic, строгий пробіг |
| Заперечення виконаної операції | Середній / середня | Audit без паролів і JWT; адміністратор ОС може змінити файл |
| Витік секретів із Git | Високий / середня | data/, ключі, БД, облікові дані ігноруються Git |
| Відмова в обслуговуванні | Високий / середня | LIMIT<=100, bounded cache, timeout; глобальні квоти ще відсутні |

JWT має sub, role, iss, aud, iat, exp, jti; строк дії — 900 с.
manager: Fleet writes і Trips writes; dispatcher: Fleet reads і Trips writes;
viewer: лише reads. bridge: outbox/ack Fleet та POST fleet-status Trips.
trips-service: Fleet reads та POST internal/trip-commands. Людський manager
не має доступу до внутрішньої команди. Дані токена не зберігаються у localStorage.

## 9. Сценарії якості з ЛР1

Нижче збережено всі вісім початкових сценаріїв з актуального локального
lab1.docx, на який уже посилався аналіз репозиторію. Новими вимірюваннями
не замінюється первинна ціль. Для нереалізованого функціоналу виконання
не заявляється.

### NFR-1: Продуктивність

Джерело: Диспетчер. Стимул: Відкриває список активних рейсів. Артефакт і середовище: API списку рейсів; Пікове навантаження 100 одночасних користувачів. Реакція: Система повертає першу сторінку з 50 рейсами. Міра: p95 часу відповіді ≤ 500 мс.

### NFR-2: Продуктивність

Джерело: Диспетчер. Стимул: Запитує побудову маршруту. Артефакт і середовище: Інтеграція маршрутизації; Зовнішній сервіс доступний; маршрут до 20 точок. Реакція: Система показує результат або контрольовану помилку. Міра: 95% запитів завершуються ≤ 3 с.

### NFR-3: Надійність

Джерело: GPS/телематична платформа. Стимул: Надсилає пакет координат. Артефакт і середовище: Приймання телеметрії; До 50 повідомлень/с. Реакція: Система зберігає валідні повідомлення без дублювання. Міра: ≥ 99,5% валідних повідомлень збережено; затримка ≤ 10 с.

### NFR-4: Надійність

Джерело: Адміністратор. Стимул: Відбувається збій застосунку. Артефакт і середовище: Вебсистема та база даних; Звичайний робочий режим. Реакція: Система відновлює обслуговування після перезапуску. Міра: RTO ≤ 30 хв; RPO ≤ 5 хв.

### NFR-5: Безпека

Джерело: Неавторизований користувач. Стимул: Намагається відкрити дані рейсів. Артефакт і середовище: Автентифікація та авторизація; Користувач не має активної сесії або відповідної ролі. Реакція: Доступ заборонено, подія записана в журнал. Міра: 100% таких запитів відхиляються; журнал містить подію ≤ 2 с.

### NFR-6: Безпека

Джерело: Адміністратор. Стимул: Змінює роль користувача. Артефакт і середовище: Керування доступом; Адміністратор автентифікований. Реакція: Система перевіряє права та журналює зміну. Міра: 100% змін ролей мають запис аудиту.

### NFR-7: Підтримуваність

Джерело: Розробник. Стимул: Змінює правило нагадування про ТО. Артефакт і середовище: Модуль бізнес-правил; Є автоматизовані тести та CI. Реакція: Зміна не потребує редагування не пов’язаних модулів. Міра: Типова зміна реалізується ≤ 4 год; тести проходять.

### NFR-8: Модифікованість/інтеграція

Джерело: Адміністратор. Стимул: Зовнішній сервіс сповіщень недоступний. Артефакт і середовище: Інтеграція сповіщень; Недоступність до 10 хв. Реакція: Основні операції з рейсами продовжують працювати; повідомлення повторюються. Міра: Основні API доступні ≥ 99% часу збою; повторні спроби починаються ≤ 1 хв.

| NFR-1, p95 <=500 мс /100 users | Gate p95 261.852 мс, 1461 запитів, 0 помилок | Виконано локально; 300 users перевищують поріг |
| NFR-2, карти <=3 с | Немає зовнішнього routing API | Не реалізовано |
| NFR-3, GPS 50/s, >=99,5%, <=10 с | Немає ingest телеметрії | Не реалізовано |
| NFR-4, RTO<=30 хв/RPO<=5 хв | Немає backup/restore drill | Не підтверджено |
| NFR-5, заборона доступу й audit<=2 с | 401/403 та audit у тому самому виклику тестуються | Підтверджено для тестових кейсів; універсальний відсоток не доведений |
| NFR-6, аудит змін ролей | Немає endpoint керування ролями | Не реалізовано |
| NFR-7, зміна ТО<=4 год | Pure domain, тести й CI є; час людської зміни не виміряно | Підтримано структурно, не підтверджено за часом |
| NFR-8, зовнішні сповіщення outage10 хв | Локальний outbox перевірено; зовнішній канал відсутній | Частково, 10-хвилинний експеримент не проводився |

План навантаження: один Uvicorn worker, loopback, SQLite, той самий обсяг
і payload до/після; окремий HTTP client на користувача, без think time;
прогрів одним запитом; задана тривалість етапу 3 с. При перевантаженні
baseline фактичний етап довший через завершення запитів і timeout 20 с.
Результати з timeout позначено як помилки, а p95 тоді описує завершення
спроб, не час успішних відповідей. Це короткий локальний дослід, не SLA.

Кеш Fleet виміряно окремо: 1000 повторень того самого repository lookup
до/після прогріву TTL cache на тій самій SQLite. Цей результат є часом
локального Python-виклику, а не HTTP RTT.

## 10. Тести, контракти та конвеєр

Domain-тести не потребують SQLite/HTTP. Інтеграційні тести використовують
тимчасові SQLite й ASGI. Контракт Trips → Fleet задає незалежні очікування
споживача і окрему перевірку постачальника. Актуальні OpenAPI експортуються
з виконуваного коду; pipeline відхиляє розбіжність зі збереженим JSON.

Fitness: 0 сторонніх імпортів у домені; 0 циклів; 0 infrastructure-імпортів
у application; domain line coverage >=95%; p95<=500 мс при 100 users,
0 помилок і щонайменше 100 відповідей. Динамічний gate запускається окремо
без coverage, щоб інструментування не спотворювало результат.

Самостійний пакет має власні run.py, .vscode, .gitignore і .github/workflows/architecture.yml. Інші лабораторні не потрібні для виконання коду, перевірок або відтворення наведених структурних метрик. Це підтверджено ізольованим прогоном окремої копії: strict TypeScript build, 85 функціональних кейсів, 100% domain coverage, HTTP gate, негативний дослід і 9 HTTP smoke-перевірок. Доказ — docs/evidence/standalone.json. ADR-014 фіксує цю межу.

GitHub Actions: checkout → Python 3.13 + Node 24 → pinned requirements → TypeScript build → pipeline →
негативний дослід → upload evidence. Невдалий subprocess зупиняє job.
Негативний дослід додає import sqlite3 у тимчасову копію domain.py,
отримує exit 1 і доводить незмінність оригіналу. Нові регресії захищають
конкурентне закріплення ТЗ, повтор пробігу, втрату відповіді, локальний
збій між двома комітами та оновлення номера у проєкції.

Аудит за файлами, рівнями, кількістю і фактичним часом — `docs/TEST_AUDIT.md`.
Контрактні й architecture-тести виділено окремо; інтеграційні ASGI-тести
не називаються наскрізними. Окремий live_smoke запускає справжні HTTP-процеси.

## 11. Прийнятий технічний борг

| Спрощення | Чому прийнятне зараз | Умова перегляду |
|---|---|---|
| SQLite, один worker | Простий автономний навчальний запуск | Конкурентні записи або p95>500 мс на цільовому навантаженні |
| Локальний TTL cache | Один інстанс власника | Другий інстанс: distributed invalidation/row ACL |
| Shared HS256, локальний audit | Взаємна довіра процесів на одному ПК | Зовнішній deployment: IdP/JWKS, TLS, захищений audit |
| Повтор lifecycle вручну після збою | Квитанції роблять повтор безпечним | Потреба безоператорного відновлення: durable coordinator/reconciler |
| Polling outbox, без retention | Малий обсяг стенду | Ріст журналу/затримки: broker, backoff, retention, метрики |
| Немає backup drill | Навчальні демонстраційні дані | Реальні дані: резервування й вимір RTO/RPO |
| GPS/карти/рольове адміністрування відсутні | Обсяг циклу зосереджено на архітектурі | Підтверджена бізнес-потреба і окремі acceptance criteria |

## 12. План еволюції на три кроки

1. Надійне відновлення: durable lifecycle coordinator, outbox retention,
   backup/restore drill. Тригер — експлуатація без оператора або реальні дані.
   Критерій: recovery після збою не потребує ручного повтору; вимір RTO/RPO.
2. Промислова межа довіри й зберігання: TLS, IdP/JWKS, PostgreSQL, метрики,
   квоти. Тригер — доступ поза localhost чи конкуренція записів. Критерій:
   той самий CI, contract tests і ціль NFR-1 на цільовому середовищі.
3. Зовнішні інтеграції: карти, телематика, сповіщення через адаптери.
   Тригер — погоджені сценарії NFR-2/3/8. Критерій: окремі навантажувальні
   й outage-тести, включно з 10 хв недоступності каналу.

перевірюваними бізнес-правилами, ролями, outbox/inbox і вимірною швидкодією.
Зміни меж пояснюють ADR, а поточні обмеження мають конкретні тригери.
