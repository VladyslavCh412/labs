# ADR-011: Збережений життєвий цикл рейсу і повторювані команди

Дата: 2026-11-03. Статус: Прийнято. Доповнює ADR-003/005/010.

Контекст: доменні start/complete були протестовані, але не доступні через
HTTP; mileage не зберігався. Розподілений збій може статися після зміни Fleet
і до локального commit Trips. Спільна БД порушила б володіння даними.

Альтернативи: залишити лише domain demo; спільна транзакція/БД; 2PC;
власні транзакції з durable command receipts і повтором. Обрано останнє.

Рішення: TripUseCases залежить від доменних TripStore/FleetGateway.
Fleet виконує start/complete у BEGIN IMMEDIATE: перевіряє ТЗ/водія,
зберігає vehicle_usage, outbox і квитанцію trip_id:operation атомарно.
Повтор з іншим payload — 409; той самий повтор повертає попередній результат.
Trips після успіху Fleet атомарно зберігає свій стан і receipt; його запис
захищений перевіркою попереднього стану. Кеші інвалідуються при змінах.

Наслідки: пробіг не подвоюється; ТЗ не займають два рейси; відмова після
віддаленого commit відновлюється повтором тієї самої дії. Тимчасова
неузгодженість можлива. Durable автоматичний coordinator не реалізовано;
для unattended роботи потрібен reconciler з збереженими pending commands.

Докази: test_lifecycle.py — concurrency, payload conflict, lost reply,
local failure, persistence, service-role boundary; live_smoke — реальні HTTP.
Умова перегляду: production або вимога автоматичного recovery без користувача.
