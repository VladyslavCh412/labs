10. ADR-002: Вибір технологічного стека
Статус: Прийнято для навчального прототипу, відповідність продуктивності підлягає перевірці.
Контекст: Для обліку автопарку, маршрутів і рейсів потрібен зрозумілий REST API, реляційне сховище, автоматизовані тести та простий запуск проєкту на комп’ютерах учасників без додаткового сервера СУБД.
Розглянуті альтернативи: A) Python + FastAPI + SQLite. B) Python + Django REST Framework + PostgreSQL. C) Java + Spring Boot + PostgreSQL.
Рішення: Python 3.12, FastAPI, Pydantic, Uvicorn, SQLite, автоматична специфікація OpenAPI, pytest і Git. Для міграцій бази застосовувати версійовані SQL-скрипти. Після декомпозиції в ЛР3 кожен сервіс використовує власний SQLite-файл.
Аргументація: Обрані засоби достатні для навчального веб API, бізнес-правил, тестування та демонстрації взаємодії сервісів. FastAPI забезпечує перевірку схем і автоматичну документацію. SQLite усуває необхідність адміністрування окремого сервера БД, що виправдано для невеликого локального стенду. Компромісом є обмежена масштабованість конкурентних записів.
Наслідки: Позитивні — просте налаштування, швидкий запуск, мінімум інфраструктури, зручна перевірка API через /docs. Негативні — SQLite має обмеження під високим паралельним навантаженням, тому результати локального стенду не можна автоматично переносити на промислову систему. Модульні межі та абстракції репозиторіїв спрощують подальшу заміну СУБД.
Умови перегляду: Якщо вимірювання покажуть неприйнятну затримку за цільової кількості одночасних користувачів, часті конфлікти запису або вимогу окремого промислового розгортання, створити новий ADR і розглянути серверну СУБД, наприклад PostgreSQL.
