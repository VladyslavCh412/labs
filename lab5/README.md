# FleetFlow — зручний вебінтерфейс для лабораторної №5

## Швидкий запуск на Windows

**Закрийте попередні три термінали** з Fleet, Trips та Event Bridge (Ctrl+C). Дані у папці `data/` зберігаються.

1. Відкрийте папку `C:\lab5` у VS Code.
2. Запуск у PowerShell:
   ```powershell
   cd C:\lab5
   .\.venv\Scripts\python.exe launch.py
   ```
3. Браузер відкриє **http://127.0.0.1:8000**. Якщо не відкрився — введіть адресу вручну.
4. Для зупинки всіх сервісів достатньо **Ctrl+C в одному терміналі**, де запущено `launch.py`.

Панель має розділи: **Огляд**, **Автопарк** (список, зміна статусу, додавання автомобіля та водія), **Рейси та маршрути** (створення й перегляд), **Дані та події** (хіти кешу, інвалідація, локальні копії та outbox). Для показу кешу натисніть **«Перевірити кеш»**. При зміні статусу Fleet генерує `VehicleStatusChanged`; bridge доставляє його до Trips. Сторінка автоматично оновлюється.

Нові автомобілі, водії та маршрути створюються через **HTTP API відповідного сервісу**, незалежні SQLite-бази залишаються розділеними. `launch.py` запускає 4 процеси: Fleet (8101), Trips (8102), Event Bridge, вебпанель (8000) і прив'язує HTTP-сервери лише до `127.0.0.1`. Якщо порти зайняті, зупиніть старі процеси.

**Це локальна навчальна панель без авторизації. Не публікуйте порти 8000/8101/8102 в інтернеті.** Не завантажуйте в GitHub `data/`, `.venv/` та локальні SQLite-файли.

# Лабораторна №5 — Архітектура даних (варіант 12)

Продовження ЛР2–ЛР4: **«Управління автопарком та маршрутами»**.

Стек: **Python 3.12+, FastAPI, SQLite, httpx, pytest**. Без Docker, PostgreSQL, Redis, хмарних ключів.

## Що реалізовано

1. **Володіння даними:** Fleet має `fleet.sqlite` (автомобілі, водії, журнал подій); Trips має `trips.sqlite` (рейси, маршрути, повідомлення та read-only проєкція `vehicle_snapshot`). Немає прямого доступу сервісів до чужої БД.
2. **Міграції:** SQL-файли `fleet_service/migrations/001_expand.sql` ... `004_contract.sql`. Перехід `plate` → `registration_number` з підтримкою старого запиту до етапу contract, паралельним записом і фінальним видаленням старої колонки. API надалі використовує звичне поле `plate`.
3. **Кешування:** локальний кеш GET `/vehicles/{vehicle_id}`: ключ `vehicle_id`, TTL **30 с**, інвалідація при PATCH статусу/номера, промах завантажує дані з Fleet SQLite.
4. **Узгодженість:** Fleet створює `VehicleStatusChanged` у локальному outbox у тій же транзакції, що зміна статусу. Окремий `event_bridge.py` передає подію **через HTTP** у Trips, який застосовує її до `vehicle_snapshot` з `event_id`-ідемпотентністю; тільки після успішної відповіді bridge ACK-ає подію на Fleet.
5. **Вимірювання:** `verification/benchmark_cache.py` — 1000 читань без кешу vs hit у RAM на тих самих даних. Це **не** HTTP-бенчмарк і не прогноз роботи у продакшені.

## Важливо про обмеження

- Локальний RAM-кеш окремий у кожного процесу. Він придатний для навчального експерименту; в реальній багатопроцесній системі знадобиться загальна інвалідація або розподілений кеш.
- За нормальної роботи bridge з інтервалом `0.5 с` оновлення read-моделі зазвичай триває приблизно інтервал опитування + HTTP-час. **Гарантованої максимальної затримки немає** при тривалій недоступності bridge чи сервісів.
- Вбудовані endpoint-и доставки подій не призначені для відкритого доступу в інтернет без автентифікації; запускати лише на localhost. Вхід і ролі будуть у ЛР6.
- Початкові контракти ЛР3 збережені, API `GET /vehicles/{id}` і `POST /trips` продовжують працювати.
