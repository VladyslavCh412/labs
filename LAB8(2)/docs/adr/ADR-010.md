# ADR-010 Обмежений кеш сторінок Trips

Дата: 2026-10-27. Статус: прийнято. Доповнює ADR-007, не змінює його пороги або початкові вимірювання.

Контекст: у першому GitHub Actions запуску 40492118294 ЛР7 отримала p95 516.807 мс за 100 користувачів проти порогу 500 мс; ЛР8 пройшла на іншому runner. Усі функціональні тести пройшли. Repository p95 ЛР7 становив 216.25 мс: одночасні однакові читання створювали зайві SQLite-з’єднання й конкуренцію.

Альтернативи: послабити поріг (відхилено, суперечить ЛР1); просто повторювати тести до зеленого (не усуває причину); Redis (додаткова інфраструктура); bounded cache з явною інвалідацією.

Рішення: кеш читання сторінок у самому Trips. Ключ `(limit, offset, active)`; TTL 1 секунда; максимум 128 записів; single-flight через Lock при промаху; інвалідація всіх сторінок після успішного create_trip_and_publish. Кеш зберігає лише JSON-проєкцію; він не змінює власника даних. Перевірка токена і ролі відбувається в middleware до звернення до кешу. Усі дозволені ролі зараз бачать однакову проєкцію.

Наслідки: однакові читання не відкривають SQLite на кожен запит. Кеш локальний для процесу; в іншому процесі чи при зовнішній зміні БД дані можуть відставати до 1 секунди. Перед додаванням нових записувальних endpoint або row-level ACL необхідно додати інвалідацію / розширити ключ та перевірки ізоляції. Довгі промахи серіалізуються, але loader обмежений SQL LIMIT і не викликає мережу.

Доказ: tests/test_read_cache.py перевіряє TTL, capacity, конкурентний single-flight та негайну видимість нового рейсу. Поточний набір має 71 перевірку. Перший невдалий хмарний прогін не приховується; результат наступного прогону доступний у Actions.
